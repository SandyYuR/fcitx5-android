# 用户工具包的触摸／画面对照

这是一套测试工具，不进入 APK 主程序。基线是默认分支
`cecea4940bb5a5db67f91d6b20e00ee5c97877ea`，直连版是
`cfd0ddc4d92dbcfcee815089ca34b97bdfa95780`；两者的 Rime prebuilt 均固定在
`1126616c3ec569617da772e30d7a97f6b2694172`。独立 checkout 仅注入相同的
`androidTest`，构建前检查主程序源码没有修改。默认分支不接收改动。

## 工具来源与调整

用户提供的《输入法性能对比报告与测试工具包.zip》采用按键触摸、录屏、区域压缩、
逐帧差分，原 ZIP SHA-256 为
`0f4b36b6c637369162e3f363628dde53475e933ed642b5b60bb37ceeacc66883`。
这里原样使用其中的 `BenchTrace.java`：
SHA-256 `fe4c318b71acb700b101304873dd586b91ee7673ef3d1da19c93b02a8aa38454`。
它不是本项目原创代码；工具包未附独立许可证，本目录只留用户指定测试所需的一份源文件，
不把原报告中的其他输入法数据写成这次结果。

- Windows 路径、1200×2670 和笔记应用坐标改为 Linux／Android 实际键位与中立编辑器。
- 原工具的固定编码串不是全拼，改用 `run.py` 中固定的 32 个全拼片段，含两个较长短句。
- 触摸仍走 Android 输入分发和真实输入法窗口，由相同 instrumentation 注入 DOWN／UP；
  DOWN 返回后等待 32ms 再注入 UP，避免每键启动一个 `adb input` 进程造成节奏失控。
  实际按住时间还包含同步分发等待；没有单独记录 UP 时刻，不宣称它精确等于 32ms。
- 保留四行键盘、三行候选和十六行编辑区的压缩与帧差流程，RGB 差阈值固定为原工具的 60。
  两版统一关闭按键气泡与水波纹，避免气泡遮住候选区被误判为引擎响应。
- **不使用原 `final_latency.js` 按候选响应最短来寻找时钟偏移的做法**。
  编辑器的独立色块在输入前后各变色六次，记录 Choreographer 帧时钟，映射视频 PTS。
  候选和提交结果不参与对时；保留所有色块残差与前后漂移，异常直接报错。
- 对照实际视频帧时间，不假设 120Hz。结果包含 32ms 按住时间、输入分发、引擎、编辑器、
  渲染和录屏采样，不称为纯引擎耗时或物理屏幕触摸到光子的延迟。

## 配置及正确性

v18.1.3 base 与官方 LTS 模型均验 SHA-256，仓库保留用户原样提供的两份 YAML。
LTS 在测试准备期间于 2026-10-17 09:59:19 UTC 更新，本工具固定该 asset 650124920，
模型 SHA-256 为 `1849e5e4acbdbfaf41fceeb86b739d5d0c85d574bd8a688562cba1e6beb78488`。
旧 API 回放的模型固定值保持原样。LTS 是可变标签，以后哈希不符时应核实上游版本，
不能直接取消校验；复现本次结果需要保留这份模型。
用户要求开启上下文调频，但 `user.yaml` 没有保存 `context_reorder`。校准发现直连版
重建输入会话会丢失临时开启状态，因此 `runtime_config.py` 给两版的测试副本统一补入
`var/option/context_reorder: true`，其余字节不变。`wanxiang.custom.yaml` 完全不变。
测试还断言真实编辑会话中“上下文开／简码开／小字集”实际存在。
模糊音、页大小 6、候选注释等其余配置均保留。所有有效方案与开关随每轮结果存档。

每轮停止另一输入法，恢复同一测试版 `user.yaml`，清除专用 `screen-bench` 的学习数据库，
相同硬件按键预热后清空编辑器。未提供用户词库和手动排序历史，因此是相同初始学习
状态的对照。先对一遍／两遍语料分别跑硬件按键参考，再断言两版及每轮触摸的完整
提交文本一致。候选像素变化少不能据此判为丢键；相同候选可能不重绘。

完整矩阵为固定 160ms × 三轮／版、120ms × 一轮／版、固定种子 90–230ms 抖动
× 一轮／版。轮次交替先后顺序，在同一 GitHub KVM 模拟器依次运行。
`--pilot` 只做八个词的预检，不能替代完整矩阵。
上述间隔是计划值。工具采用同步 Android 注入，系统繁忙时实际按键会迟到；
必须同时报告实际间隔和超期，不能把计划节奏说成严格一致的实际压力输入。

## 运行和产物

在功能分支手动运行 `Wanxiang touch and screen comparison`，先输入 `pilot=true` 校准；
校准通过后输入 `pilot=false` 跑完整矩阵。可传入通过校准的
`reuse_run`，直接下载其 APK 并校验 instrumentation 源码哈希，不重新构建产品。
工作流安装 Android 35 Google APIs x86_64 模拟器，保留视频、截图、逐帧 TSV、视频 PTS、
实际注入时刻、模型和 APK 校验值、有效方案、硬件参考文本及结果。
视频和模型不进 Git；小型结果和方法说明归入直连版维护文档。
结构化结果与视频分为两个 artifact，保存 14 天；永久归档保留配置、实际事件、
逐帧轨迹、时钟残差、版本及校验值。`summarize.py` 取每轮分位数的中位数并保留范围，
不把同一轮内的几百个相关按键当作几百次独立实验。

`forward_candidate` 是每键之后的下一次候选区域变化；未改变画面的键可能匹配到
后一个键的变化。`attributed_candidate` 是画面变化归到之前最近一键，不能称为纯
引擎耗时。另列出下一键之前发生的首次候选变化及覆盖率，避免将等待后续按键
当作引擎成本。上屏指标只取空格提交，避免把等待后续拼音输入的时间算作提交延迟。

`analyze.py` 的变化像素门槛为候选 ≥5、编辑区 ≥2；它与原样使用的 RGB 总差阈值 60
是不同参数。原 `final_latency.js` 使用候选 >25、编辑区 >15，最终报告还从同一份轨迹
复算该门槛的敏感性，不据此重新选择主分析指标或调整对时。
