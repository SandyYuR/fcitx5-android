# 首个 i 分发等待复核与性能补丁撤回（2026-11-12）

**本轮没有证明候选性能补丁能带来稳定收益，因此已撤回这些产品改动。** 当前 [PR #32](https://github.com/SandyYuR/fcitx5-android/pull/32) 仅保留“字体变化时清理自定义文字测量/绘制缓存”的正确性修复，以及固定节拍探针、事件分析和既有候选设备回归。没有将未证实的性能优化合入默认分支。

用户主要关心旧表 **11.141 → 39.814ms** 的测试回退。原始记录保持不变；它确实记录了更长的等待，但该区间的起点由响应驱动的探针决定，不能单独证明应用整体或 librime 计算慢了 3.57 倍。本轮修正了测试方法，并用多组对照核对这一区别。**本报告不宣称首键或图形同步长等待已经消除。**

代码和工具最终来源为 `10cc633175ce3cb832e2ab098497c34915e291e7`；本页全部性能表对应此前各个明确标记的试验版本。最终交付源码没有再次进行性能计时，不使用撤回版本的数值作为它的性能证据。

## 旧指标为什么会改变方向

旧探针每轮执行：点击 n → 等待 n 的编码事件 → 在主线程查找 i 键 → 同步注入 i 的 DOWN → 等待 20ms → 同步注入 UP。`i` 的实际发出时间受前面阶段、主线程查找和注入器调度影响。

AOSP Android 15 的参考实现还显示：`UiAutomation.injectInputEvent(event, sync)` 默认传入 `waitForAnimations=true`，`UiAutomationConnection` 在 DOWN 前和 UP 后调用 `WindowManager.syncInputTransactions`。**把 sync 改成 false 也不会移除这两个表面事务同步。** 参考源码、许可证头、URL 和摘要在[附件](./framework-reference.zip)中；它们是参考实现，未冒充从模拟器提取的 framework 字节。

旧表的 UP 时间记录于注入调用之前，终点为 IME 窗口接收 UP。这个等待真实发生；但前面的同步也会推迟后续事件的提交，导致延迟落入“发键之前”或“发键之后”的不同区间。下面的跨阶段指标均先在**同一个进程样本**内计算，再取中位数，没有相加独立中位数。单位 ms：

| 批次/VM | 版本 | i 提交 UP → 窗口接收 UP | n 窗口 DOWN → i 窗口 UP |
| --- | --- | --- | --- |
| 四版本对照，正序 VM | 默认 `0380d70f` | 0.676 | 200.850 |
| 同上 | 候选单项 `0d9417b2` | 55.932 | 194.028 |
| 独立两版确认，正序 VM | 默认 `0380d70f` | 36.336 | 179.111 |
| 同上 | 候选单项 `0d9417b2` | 0.631 | 204.250 |

第一组的局部等待变长，i 实际接收时刻却略早；第二组局部等待大幅变短，跨阶段接收却更晚。后一个指标仍含探针操作，不能当作真实打字速度；这些结果说明不能只选一个有利的区间来宣布提速，也不能忽略原来的不利数据。

## 确认存在的图形与传输等待

原三轮的 12 份 trace 重新按同一方法检查，没有覆盖或改写旧证据。一份旧组合版 trace 的 i 等待 **79.051ms**，与主线程 `postAndWait` 重叠 **78.740ms**；主线程 CPU **0.322ms**，RenderThread CPU **74.975ms**，Rime owner 在该窗口 CPU 为 **0**。绘制线程还有约 **93.507ms** 的 EGL swap 和 **92.793ms** 的 `rcCreateSyncKHR encode` 区间。

原版 trace 同样有约 **81.200ms** 的等待；此前尚未加入发布优先级扩展的版本也有约 **82.893ms**。因此这种机制早已存在，不能归为本轮发布优先级改动新产生的固定成本。完整复核 SQL 和线程数据在[历史复核](./historical-render-analysis.zip)中。

新采集也有输入仍在传输、主线程空闲而绘制线程繁忙的样本，并非每次都与主线程 `postAndWait` 重叠。具体传输阶段仍有未归因部分；不能把所有长等待都算成主线程执行，也不能把 wall time 当成 CPU 时间。

两种模拟器 GPU 启动模式 `swiftshader_indirect` / `swiftshader` 在相同宿主机轮换、反向顺序复核后，也没有形成稳定的普遍改善。启动选项不等于已证明使用了两套不同的实际驱动；实际属性和模式列表随原始附件保留。本轮没有据此修改应用渲染设置。

## 固定节拍协议及最后一版候选试验

新探针提前缓存 n/i 的坐标，计划两次 DOWN 相隔 100ms、各保持 20ms。通过测试专用 InputManager 异步注入，避免每键 UI 查找和 UiAutomation 表面同步；反射与 Shell 注入权限仅用于测试进程，不进入产品 APK。窗口回调核对实际触摸目标并记录时间，错误坐标使测试失败。

分别记录：计划 UP → 实际提交、实际提交 → 窗口接收、计划 UP → 窗口接收。等式只在同一次事件内成立，不能相加各自的中位数。快速输入允许中间 n 展示合并；探针不为缺少的 n 展示伪造 native 终点。选词在 ni 展示到达并等待 UI 空闲后进行，**其点选数值不能直接与旧协议的首次点选表比较**。

下面是最后的 `b03e9b46` 候选试验，每版每 VM 6 个无 trace 新进程，单位 ms。**这套候选性能改动随后已撤回。**

| --- | --- | --- |

## 验证与保留限制

两个分项构建各执行 131 项目标 JVM；最后候选试验 `b03e9b46` 也执行 131 项，失败/错误/跳过为零。ARM64/x86_64 Debug 构建、APK 白名单、16 KiB 对齐及原生链接审计通过；该试验包的三项原生库仍为 direct-rime、C++ 运行时和 QuickJS。它们均属于已撤回候选试验的验证，不能改记为当前字体修复的性能验收。

当前字体缓存修复及永久工具的验证记录见[最终代码 CI](./code-ci.json)。实际 Android 前端报告有 **51 项用例，失败/错误/跳过均为零**，其中新的字体替换回归确实执行通过；见[原始设备结果](./final-font-device-results.zip)和[用例核验](./font-device-validation.json)。字体设备回归、既有角标/溢出回归、完整前端/引擎 smoke、JVM、ARM64/Debug 及原生 sanitizer 按实际 CI 记录报告。事件工具以真实 trace 复核 CPU/图形区间，并拒绝负时间区间、缺失调度、丢失/错误统计及无效触摸目标；拒绝时仍保留 SQL 和 JSON。

构建 `43147978372` 的失败发生在两个变体成功构建并各通过 131 项 JVM 之后：元数据步骤未显式获取历史重整前的 `4d77cd79`，读取其 SDK 锁失败。随后取回固定提交，在 `43149362713` 复用同一批 APK 完成校验和测量，没有通过重建替换不利样本。[失败日志](./ablation-build-failure.log.txt)保留原字节。

当前没有真机或正式 Release 的性能结论，没有可靠 P95、长期大词库或日常丢键率结论。源码重组、测试协议变化和生成版本标识均按实际来源登记。默认分支未推送或合并；历史 Actions、旧文档和原始报告没有删除。
