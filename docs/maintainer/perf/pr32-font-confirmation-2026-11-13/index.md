**字体缓存修复已通过反向验证，值得作为正确性修复保留；本轮仍不能宣布零性能回退。** 收窄后的两版完成 48 个新进程、288 次正确选词。完整首次 i 的配对区组差中位数为 +0.984ms、−11.192ms，两台 VM 各为三慢三快；首次点选窗口 UP → IC 仍为 +1.271ms、+2.646ms，保留小幅偏慢风险。后五轮稳定输入没有同方向的退化证据。

## 字体修复的反向验证

**反向验证成立。** 未修复版执行同一测试时恰好出现一项预期断言失败：新字体应为 **240px**，缓存结果仍为旧字体的 **152px**。修复版同一字宽测试通过，另外三项候选像素／渲染测试也全部通过，失败／错误／跳过为零。

原始失败首行：`java.lang.AssertionError: Unchanged text must use the new font's width expected:<240> but was:<152>`。

测试先显示不变的 `MMMMMMMM`，从 MONOSPACE 更换为 SERIF，重新测量后与新 Paint 的实际字宽比较。未修复版与修复版执行同一份测试；只有基线出现确切的旧字宽断言失败才接受反向验证，其他异常、跳过或意外通过均使任务失败。基线的预期失败不会被改写为“全部测试通过”。

修复版还执行三项设备渲染测试，覆盖浅／深主题、普通／溢出模式、正文／注释及空白注释切换、高亮颜色与像素、正文和注释字体／字号刷新。[原始契约结果](./font-contracts.zip)包含 instrumentation 文本、JUnit 和日志；负向控制在单独 VM 执行，未暖机或污染性能对照 VM。

这验证的是字体变更后的显示正确性，不能单凭它推断输入提速。相同字体引用不会触发新增的失效分支；真正换字体仍需要重新测量和布局。

## 性能方法与结果

计划在 dispatch 前提交，见[预登记](./font-confirmation-plan.json)。两台 API 35 AOSP ATD x86_64 KVM VM 使用软件图形，每台随机排列恰好三个 ABBA 和三个 BAAB 区组。每个区组包含两次 baseline 和两次 current，各产品先求均值再相减；**一个区组是一个配对观察**。每次进程前卸载重装并恢复同一夹具，n/i 计划间隔 100ms，实际注入至少按住 20ms；不注入暖机文字、不采 trace。

两边使用同一个独立 shell app_process 发键器。IME 仅观测窗口与后端事件，中立编辑器记录 InputConnection 入口。这个驱动与永久 v2 Kotlin 探针分开标识，不能混同为同一个探针已运行。采集器验证保持策略、真实时序、坐标、模型映射和正确提交；失败前保留原始 IME JSON。

| forward | i 实际 DOWN → 窗口 UP | 78.420 | 79.571 | +0.984 | -12.134～+24.471 | 3／3 |

正值表示 current 较慢。每版在每台 VM 有 12 个首次值、6 个配对区组；首次与后五轮的进程内中位数分开，后五轮不是五个独立进程。配对中位数不是两列绝对中位数直接相减。

完整首次 i 在 forward 六个区组为三慢三快，reverse 也为三慢三快；reverse 区组差可达 −78.222～+81.868ms，不能把其中位数的负值宣布为提速。首次 i 实际 UP → 窗口 UP 的配对差为 −4.296ms、−10.997ms；各阶段的中位数不满足可加性，不能相加解释完整链路。两台 VM 的绝对首次 i 中位数相差很大，也应限制模拟器数字的外推。

**首次点选风险仍需保留。** 窗口 UP → IC 的区组差中位数两台 VM 都为正；forward 四慢两快、reverse 三慢三快，区组差范围分别为 −2.949～+4.281ms、−8.140～+7.170ms。这不是每个区组都固定慢 1～3ms，也不足以证明已无回退。外部实际注入 UP → IC 的对应差为 +0.189ms、+2.467ms，说明不同时间边界会移动部分等待，但第二台 VM 仍有偏慢中位数。本轮没有 trace，不把这项差值猜定为字体测量、引擎或绘制中的唯一根因。

后五轮完整 i 的进程中位数区组差为 −0.035ms、−0.042ms；后五轮窗口点选 UP → IC 为 −0.234ms、+0.221ms。这些微小差值不能作为提速比例，也没有呈现一致的持续输入回退。

全部 864 次触摸实际保持均不少于 20ms，范围 20.147～94.789ms；实际 n/i 间隔和注入迟到同样保存在原值。修正最低保持并未创造实时调度保证。此次没有重复采集以替换不利结果，只有一轮预登记的两版正式对照。

保留建议基于两个已确认的缺陷：字体更换后仍用旧字宽，以及迟到 DOWN 会压缩测试刺激。建议把 PR 定位为字体正确性与测试可靠性修复；选词冷态的小幅偏慢尚未排除，PR 保持草稿，不按“性能回退已解决”验收。

全部区组差、首次／warm 原值、实际按住时长与迟到量见[独立复算结果](./font-confirmation-results.json)与[复算源码](./analysis-sources.zip)。正序和反序原始 ZIP 均按 GitHub artifact SHA256 核验；独立分析器逐项使用原始整数纳秒重新相减，再检查采集端完整统计。不丢弃不利区组，不因版本偏慢重跑已接纳数据，也不把本次结果与之前批次混池。

## 验证与边界

收窄提交 2e86e2ec 的六项代码 CI 成功。新设备原始 XML 实际 **59 项、失败／错误／跳过全零**，包括更新后的候选渲染测试；[设备原件](./code2e-frontend-results.zip)和[核验](./code2e-frontend-validation.json)保存来源。它们与本轮字体负向控制、性能采样分别报告。

本轮保留原有方案功能。候选 comment 中仍可能有“+”类型标记；撤下快路径本身不是对原有数毫秒偏差根因的证明。字体失效仅在字体引用改变时发生，性能对照用于检查其实际输入成本，而不是从代码行数推断零开销。

最低保持 20ms 不是实时调度保证；模拟器的 DOWN 迟到、实际保持和软件图形仍可能大幅波动。首次样本包含卸载重装后的缓存成本，键盘、方案绑定已就绪后才发键；不能等同于日常进程重启或绑定尚未完成时的首键。ni 终点是事件观测、IC 终点是编辑器入口，均非屏幕发光。没有真机、Release、长期个人词库、可靠 P95 或总体吞吐率结论。
