# 2026-11-08 冻结版本：万象与旧 Fcitx 版性能复测

本轮只比较两版产品：请求开始时远端默认分支 `fx-rime-only@2e48466e`，以及 PR #4 合入前最后的默认分支 `5fb6bca3`。万象更新到本轮冻结时最新稳定版 **v18.1.10 base + 2026-11-07 LTS 模型**，继续使用用户上次的两份 YAML、全拼、上下文调频、简码、小字集。

测试在 2026-11-08 执行，报告于 2026-11-11 整理。本轮观察到：**正式包的候选点选到编辑框变化更快，Debug 常速 CPU 时间更少，PSS 略高；画面对照不足以证明稳定的整链路提速。**

| 主要项目 | 旧 Fcitx | 直连版 |
| --- | --- | --- |
| Release 单字首次点选 → TextWatcher，中位数 | 32.45ms | 16.31ms |
| Release 短语首次点选 → TextWatcher，中位数 | 33.35ms | 24.23ms |
| Debug 常速进程 CPU，三轮中位数 | 35,797ms | 28,030ms（约低 21.7%） |
| Debug 常速 PSS，三轮中位数 | 381.81 MiB | 390.54 MiB（约高 8.73 MiB） |

被测直连源码是任务开始时默认分支的 `2e48466e`，之后默认分支的新增提交没有倒填为本次实测版本。所有结论限定于下述配置与模拟器。

录屏仍沿用用户原工具的 BenchTrace、RGB 差分与独立色块对时，不按“最快候选延迟”拟合时钟。原默认阈值 RGB sum 60、候选变化像素 ≥5、编辑区 ≥2；另检查更严格检测阈值对结论的影响。颜色标记前后共 12 个；残差跨度 >50ms 或前后漂移 >34ms 的录屏不接纳延迟。屏幕采样仍是软件录制，CPU onDraw 与视频画面均不能等同于面板实际发光。相邻键可以没有可见候选变化，“下一次候选变化”可能对应后面的键，所以还报告本键窗口覆盖率及共用事件，不把未检测到画面变化解释为丢键。匹配只在 500ms 窗口内计数，超窗/无变化项单列；因此画面 P95 是已匹配变化的 P95，不能据此排除所有超过 500ms 的长停顿。

录屏的正确性是触摸输出与同语料硬键参考一致，包含模糊音与方案本身的首选策略，不是语言学上的首选词准确率。没有导入用户日常使用的历史用户词库，因此不能覆盖大用户库、多个输入法共用目录或长期学习负载。

录屏每轮使用相同方案、干净学习状态和相同预热；录屏不是冷启动。正式包每次恢复各自同一份完整已部署快照，保留共同校准词“你、早上好”的学习轨迹及引擎生成的指纹/构建时间，不导入个人历史词库。共享资源和配置文件的纳秒修改时间逐项恢复并读回核对，防止重装触发意外重新部署。CPU 为输入期间进程 CPU ms，PSS 为输入结束采样，不能拿 APK 大小或 OS 页缓存作进程内存。两个产品分别保留自己的学习库和编译产物；不混用快照。首次部署和资产释放不进入选词计时。正式包每个产品/词例安排 6 次新进程，每进程每阶段 8 次选择，分别检查首次唤起与离开编辑器再返回；热态先算每进程中位数，再跨进程汇总，避免将同一进程内相关样本当作独立重复。

## 触摸、画面与资源的正式结果

[完整汇总](./screen/comparison.json) · [独立派生表](./screen-derived.json) · [对时复核](./screen/clock-checks.json) · [原始结果 ZIP](./screen-results.zip)。正式录屏任务为 [42469711691](https://github.com/SandyYuR/fcitx5-android/actions/runs/42469711691)，不是前面的校准批次。

14 轮均完成，4 个硬键参考互相一致，10 个触摸轮次共 **4,752 键**，每轮最终文本均与对应参考一致。录屏共用内置 26 键布局，实际字母键边界在两版中一致。所有触摸轮次在末尾标记后的第一次外部观察时，文字已完整；这只说明该观察点没有残留待送达文本，不能反推每个按键都没有积压。

### CPU 与 PSS

CPU/PSS 使用全部文本正确的轮次；画面时钟校验不影响这两个进程内采样。常速每轮 528 键、64 次空格提交，3 轮取中位数，括号为三轮范围。

| 常速资源项目 | 旧 Fcitx Debug | 当前直连 Debug |
| --- | --- | --- |
| 输入期间进程 CPU 时间 | 35,797ms（35,201–35,833） | 28,030ms（27,767–28,265） |
| CPU 时间 / 输入键数 | 67.80ms/键 | 53.09ms/键 |
| 输入结束 PSS | 381.81 MiB（379.24–382.30） | 390.54 MiB（390.35–391.00） |

当前版该工作负载的累计 CPU 时间约低 **21.7%**，PSS 高 **8.73 MiB（约 2.3%）**。CPU 包含输入法、渲染与测试探针所在进程的工作，PSS 为单点采样；两者都不能直接换算为真机续航或生产版开销。

快速目标轮与抖动轮也分别完整执行，但各只有 1 轮：CPU 为 `35,073→27,309ms`、`17,570→13,627ms`，PSS 为 `384.25→391.47 MiB`、`387.49→392.76 MiB`。不与三轮常速混池，也不将这些单轮差异当作长期统计结论。

有效配对的快速目标轮如下，单位 ms，均为 DOWN 起算的已匹配画面变化：

| 画面指标（各 1 轮） | 旧 Fcitx | 当前直连 |
| --- | --- | --- |
| 下一次候选变化 P50 / P95 | 154.94 / 414.74 | 166.44 / 412.14 |
| 空格至编辑区变化 P50 / P95 | 126.24 / 437.74 | 138.14 / 347.84 |
| 本键窗口内候选变化覆盖率 | 62.88% | 62.69% |

这一个配对没有显示候选 P50 提速，编辑区 P95 方向较好，但不足以支持稳定的整链路提升。当前版三轮有效常速的候选 P50 中位数为 **162.20ms**，缺少同条件有效旧版值，不能拿历史 PR #4 的 119.7ms 来补成新对照。

更严格的像素检测（候选 >25、编辑区 >15）下，该快速配对候选 P50 仍为 `154.94→166.44ms`，编辑区 P50 变为 `213.84→290.64ms`。编辑区结果对阈值明显敏感，说明不能把这种差分数值解释为精确的每次 `commitText` 耗时；正式 APK 的编辑器回调测量单独列示。
