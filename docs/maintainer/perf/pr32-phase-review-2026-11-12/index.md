# PR #32 独立发键与实际触摸时长复核（2026-11-12）

**已修复会误导比较的采样问题；应用的首次长等待仍然存在，本轮没有得到全面提速或回退已消除的结论。** 正式两台 VM 的首次完整 i 触摸区组差中位数分别为 −1.934ms、+13.870ms；首次点选到编辑器的区组差中位数分别为 +3.117ms、+1.851ms，继续列为未解决的回退风险。

本轮审阅用户更新后的 [PR #32](https://github.com/SandyYuR/fcitx5-android/pull/32)，冻结应用源码 e8bc4fe7，与其共同基线 0380d70f 比较。交付提交 38555944 只修正测试工具，生产路径与 e8bc4fe7 完全相同；不把旧 APK 改标为 38555944 已计时。默认分支新增的 88a664d4 引擎变体功能不在此次性能结论范围，未推送或合并默认分支。

## 为什么需要补测

- 用户新增的产品改动仅为字体测量缓存失效修复及无注释候选高亮时避免重建文字；e8bc4fe7 的生产和构建配置源码与此前正式试验的 adb6a4e3 相同。后续提交主要保护采集、恢复与时间轴校验，原始研究见[此前正式对照](../../changes/2026-11-12-pr32-latency-study.md)。
- 原 11.141 → 39.814ms 是旧批次 6 个新进程首次值的中位数，不是单次触摸，也不是后来每轮都复现的固定损失。[此前复核](../input-dispatch-2026-11-12/index.md)保存各轮相反方向及不利结果，撤回没有只依据一个表格单元。
- 最新 v2 探针已使用 InputManager 异步注入。旧 UiAutomationConnection 的每键窗口／表面同步不能继续解释这批新数据；本轮检查真实窗口分发、绘制同步，以及同进程发键器的影响。
- 关闭万象拼音注释后，实测“你”的 comment 仍为“+”，与有效配置中 super_comment/cand_type/user_phrase 的标记一致。方案的 super_filter 会独立追加类型符号。因此“注释关”不等于空注释，本夹具不能衡量无注释快路径的性能。本轮保留用户学习和原配置，没有通过清除标记或关闭功能制造快路径命中。

## 已确认并修复的采样偏差

第一次有效独立发键预演中，同一 100ms 条件的两个首次样本为：

| 样本 | i 按下迟到 | 实际按住 | 实际 DOWN → 窗口 UP |
| --- | ---: | ---: | ---: |
| baseline | 47.365ms | 0.796ms | 2.703ms |
| current | 0.588ms | 20.389ms | 28.844ms |

发键器按原定 UP 截止时间松开；DOWN 迟到后，按住时长被压缩了。这组 26.140ms 差值包含约 19.593ms 的触摸形状差，不能直接归为产品回退。原预演[正序](./pilot-forward.zip)和[反序](./pilot-reverse.zip)保留，未替换或改写。

38555944 同时修正永久 Kotlin 探针：UP 等待计划截止时间与“实际注入 DOWN＋20ms”中的较晚者。新样本声明保持策略，采集器与统计器拒绝声明策略却实际不足 20ms 的触摸；失败时先保留原始 IME JSON。旧样本仍按原探针摘要解释，不自动获得新保证。协议字符串沿用 v2，编译探针的 SHA256 与保持策略明确区分版本，旧产物不能通过当前源码摘要检查而冒充新测量。

**最低保持时长不等于实时调度保证。** 正式样本的首次 i 实际保持仍有 20.295～83.950ms，DOWN 也有迟到；全部原值保留，没有截断或删除长值。这些变量仍限制局部区间的产品归因。

SDK 锁和夹具摘要与原研究相同，模型实际映射与运行开关逐进程检查；两版都为直连版，没有重跑旧 Fcitx 或 Foxy。各 APK 的真实摘要、证书和原生链接分别保存，见[产物清单](./products.json)、[SDK 锁](./sdk-lock.json)、[基线 APK 审计](./baseline-apk-audit.json)、[当前 APK 审计](./current-apk-audit.json)及两份[基线](./baseline-native-link-audit.json)／[当前](./current-native-link-audit.json)原生审计。

API 35 AOSP ATD x86_64、KVM、软件图形；每个样本卸载重装并恢复同一夹具。这包含首次使用的缓存成本，不能等同于日常仅重启进程。键盘显示、选定方案和注释开关后才开始第一轮；没有注入暖机键，也没有预先输入词语。这里不是服务刚启动时尚未完成绑定的首键验收。

发键 API 位于独立 shell app_process，IME 仅保留窗口回调和事件观测，中立编辑器记录 InputConnection 入口。原探针的 clock 文案仍写“两进程”，实际独立协议有三个进程，以记录的 PID、driver_identity 和协议为准。字母坐标提前缓存，窗口 DOWN 检查实际目标；计划与实际提交、返回、窗口接收分别记录。n/i 的 DOWN 计划相隔 100ms，实际保持至少 20ms；点选发生于 ni 到达且 UI 空闲后。

正式计划在 dispatch 前提交进历史包：每 VM 3 个随机 ABBA/BAAB 区组，一个区组内两次 baseline 与两次 current 各取均值后相减，再汇总三个区组。每进程六次选词，首次与后五次的进程内中位数分开。**一个区组是一个配对观察，六次选词不是六个独立进程。** 100/300ms 预演、无 trace 正式数据及独立 trace 不混池。300ms 只用于定位帧相位，不当作打字提速。

## 正式结果：100ms、原配置

两台 VM 共 **24 个新进程、144 次选词全部正确**。每个产品在每 VM 有 6 个首次值、3 个配对区组。正值表示 current 较慢，单位 ms：

| VM | baseline 首次完整 i 中位数 | current 首次完整 i 中位数 | 区组差中位数 | 区组差范围 |
| --- | ---: | ---: | ---: | ---: |
| forward | 54.076 | 47.957 | −1.934 | −8.106～+3.353 |
| reverse | 79.750 | 81.982 | +13.870 | −11.408～+39.028 |

完整 i 指实际注入 DOWN → 窗口 UP。表中配对差不是两列独立中位数相减；它先在同区组对两次同产品求均值，再计算差。其他阶段同样按区组计算：

| VM | n 计划 DOWN → ni 事件，区组差中位数 | 窗口候选 UP → IC，区组差中位数 | 点选区组差范围 |
| --- | ---: | ---: | ---: |
| forward | −5.003 | +3.117 | +2.603～+4.924 |
| reverse | +12.197 | +1.851 | −2.618～+3.210 |

首次点选在 forward 的三个区组均较慢，reverse 为两慢一快；不能省略这项风险，也不能沿用旧批次的“末段没有稳定损失”作为新结论。样本只有每 VM 三个区组，且仍有明显刺激时序和绘制调度差异，本轮没有确证唯一代码根因，未据此猜改候选选择、引擎或线程优先级。

全部逐进程首次／warm、七项独立整数纳秒复算、区组原值及完整统计见[结果](./phase-results.json)和[复算源码](./analysis-sources.zip)，原始[正序](./formal-forward.zip)、[反序](./formal-reverse.zip)均按 GitHub 原始摘要核验。没有删去不利区组、没有重复抽样替换已接纳数据，也没有估计可靠 P95。

## 独立 trace：长等待确在绘制阶段

独立 VM 的四个诊断进程完成 24 次正确选词；四份 trace 均无丢失／错误统计，相关线程调度覆盖完整。以下取各进程首次 i 的“实际 UP → 窗口 UP”窗口，CPU 为实际调度交集，单位 ms：

| 条件／产品 | 等待 | 主线程 CPU | RenderThread CPU | Rime owner CPU | 主线程 postAndWait 重叠 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100ms baseline | 10.029 | 2.444 | 7.674 | 0 | 4.661 |
| 100ms current | 97.925 | 0.382 | 71.688 | 0 | 97.550 |
| 300ms baseline | 1.253 | 0.311 | 0 | 0 | 0 |
| 300ms current | 0.792 | 0.234 | 0 | 0 | 0 |

这证实一份不利 current 样本主要在主线程等待绘制；该窗口不是 librime 正在计算。300ms 避开首次候选帧后等待较短，支持帧相位影响的解释，**不能据此把延后第二键说成修好了快速输入**。此前基线也有同类长等待，见[旧 trace 复核](./independent-profile-review.json)。

点选段也保留不利数据：这台诊断 VM 的窗口 UP → IC，100ms 条件为 7.682 → 11.929ms，300ms 为 8.806 → 10.652ms。对应 action_core wall 为 3.610 → 5.085ms、3.058 → 7.082ms，CPU 为 1.447 → 1.534ms、1.274 → 1.692ms；wall 与 CPU 不等价。这些是独立诊断样本，不能冒充正式无 trace 对照或确定的产品效果。

[输入窗口摘要](./held-profile-summary.json)、[点选阶段](./select-profile-summary.json)、[逐事件 SQL／调度](./held-profile-analysis.zip)和[原始 trace](./held-profile.zip)保存完整来源。分析器最初沿用 100ms 固定校验，正确拒绝了 300ms 对其旧约束的输入；随后只为独立相位协议按声明的 100/300ms 校验，未修改原始事件或放宽调度／丢失检查。[原拒绝记录](./analysis-validator-before-gap-adaptation.zip)保留。
