## 部署重载

原来的重新部署确实调用了 `start_maintenance(true)` 并销毁会话；按钮没有消失不能单独证明它没有执行。
但仅销毁会话不能清除 Lua `require()` 的模块缓存，已加载脚本可能继续使用旧内容。
此外，强制维护在启动线程前失败时会返回 false，旧代码只依赖部署通知，可能漏报这类失败。

现在显式部署先结束旧会话并清空候选/预编辑/状态动作，再执行
`finalize → initialize → start_maintenance(true) → join → 读取方案列表 → 新会话`。
`finalize` 释放组件和 Lua 运行环境，并关闭、持久化用户数据库。
完整部署仅失效 `build/` 中有对应源文件的生成 YAML，保留原始配置、词典/模型二进制、无源预编译方案与所有用户库、同步记录。
这也处理复制文件保留原修改时间的情况：上游配置编译器只比较秒级 mtime，`full_check=true` 本身不强制重编译这些 YAML。
初始化 glog 的 `setup` 仍只执行一次。目录切换直接完整初始化，不重复进行增量与完整部署。
部署入口使用互斥锁串行执行，期间拦截按键并显示忙碌提示，成功后恢复当前可用方案与状态区。
强制维护返回 false 或发出 failure 都视为失败；修改文件后可再次部署恢复。
日常唤起键盘仍按原有规则复用普通文本会话，不在输入热路径增加初始化。

新增设备回归 `redeployReloadsLuaAndSchema`：先加载 Lua 以填充缓存，修改模块顶层常量、方案名、开关和
`schema_list`，分别经设置部署与状态区部署，验证实际候选注释、可选方案、开关、中文提交和无重复提交。
同一个 Lua 过滤器同时验证发行代号和 APK 版本，避免只检查 UI 文案或 ELF 中的字符串。
回归还刻意保持 YAML 修改时间不变，确保显式部署实际刷新内容；原生契约检查启动保留缓存、部署仅失效生成 YAML，
并验证用户库、词典二进制、无源预编译配置及符号链接目标均保留。
原生契约还覆盖完整卸载/初始化次数、setup 仅一次、维护线程未启动的失败及失败后的再次部署。

## 包名与统计名称

主应用恢复为默认分支实际包名 `org.fcitx.fcitx5.android.fx.rime`，Java/JNI 的命名空间不变。
签名相同时可覆盖原包名旧版；旧测试包 `io.github.sandyyur.rime.direct` 的数据不会自动跨包搬移，
先备份、恢复并检查后再卸载测试包。详细步骤见[用户手册](../manual/DIRECT_RIME_USER_GUIDE_zh-CN.md#备份迁移与升级)。
最小诊断应用使用独立的 `.lab` 包名，避免与主应用互相覆盖。

万象的 `input_statistics.lua` 读取 `rime_api.get_distribution_code_name()` 和
`get_distribution_version()`。现将 `distribution_code_name` 与 `distribution_name` 设为 UTF-8 中文“中州鹅”，
版本通过 JNI 从当前 APK 的实际版本传入，不再固定为 `direct-rime 0.1`。
这不是新增或重命名输入方案；万象、空格键方案标签及技术库名不因发行名称变化而更改。
